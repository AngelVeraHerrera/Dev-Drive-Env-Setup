GSTREAMER CHECKS
=======================================================================
Run these from the environment's own launcher. See ../README.txt for why
that is not optional.

VIDEO=$DEVDRIVE_ROOT/testing/gstreamer/videos/FPS_test_1080p60_L4.2.mkv

A note on what is and is not available, because a command that names a
missing element fails in a way that looks like a broken install:

  * The d3d11 family (d3d11h264dec, d3d11h265dec, d3d11videosink,
    d3d11screencapturesrc, d3d11download) needs directxmath, and d3d12
    needs directx-headers. Both are declared by the gstreamer overlay
    port, so they are present. Without them the plugins vanish SILENTLY
    and the first complaint comes from somewhere unrelated.

  * Media Foundation works, but only as far as the machine does.
    mfh264enc, mfaacenc, mfmp3enc, mfvp9enc, mfvideosrc and the MF
    decoders are all present. mfh265enc is NOT, and that is the hardware
    and the OS rather than the build: MF registers an encoder only when
    the system offers a matching transform, this GPU has no HEVC encoder
    (Kepler), and the Microsoft HEVC Video Extension is not installed --
    it is sitting in <drive>:/installation as a package, unopened. Use
    x265enc for H.265 here.

    (Getting even mfh264enc took a patch: upstream's probe decides it is
    building for WinRT -- WINAPI_PARTITION_APP is true on desktop Windows
    too -- and then wants a GstWinRt library that is MSVC-only upstream,
    so the whole plugin skipped itself in silence. See delta 7 in
    installation/vcpkg_overlays.txt.)

  * glupload / glimagesink need the "gl" feature on the gstreamer port,
    which the configuration does not currently request.

  * nvcodec offers only H.264 on a Kepler-era card: nvh264enc,
    nvh264dec, nvjpegdec and the MPEG decoders. No HEVC, no AV1. That is
    the GPU, not the build -- nvcodec registers what the chip reports.

5. NVIDIA
-----------------------------------------------------------------------
# What the GPU actually offers. nvcodec enumerates from the chip, so this
# is the authoritative list, not the documentation.
gst-inspect-1.0 nvcodec

# NVENC encode straight into NVDEC decode: exercises both halves. The
# proof that it ran on the GPU is in the -v output:
#   nvh264dec0.GstPad:src: caps = video/x-raw(memory:CUDAMemory)
# CUDAMemory means the decoded frame never left the card.
gst-launch-1.0 -v videotestsrc num-buffers=300 ! \
  video/x-raw,width=1920,height=1080,framerate=30/1 ! \
  nvh264enc ! h264parse ! nvh264dec ! fakesink sync=false

# Encode to a file with NVENC.
gst-launch-1.0 -e -v videotestsrc is-live=true num-buffers=600 ! \
  video/x-raw,framerate=60/1,width=1920,height=1080 ! \
  videoconvert ! nvh264enc ! h264parse ! mp4mux ! filesink location=nv_h264_1080p60.mp4

# Re-encode the real file with NVENC.
gst-launch-1.0 -e -v filesrc location=$VIDEO ! matroskademux name=d \
  d.video_0 ! queue ! decodebin ! videoconvert ! \
  nvh264enc ! h264parse ! mp4mux ! filesink location=reenc_nv_h264.mp4

# Media Foundation encode, which is the vendor-NEUTRAL hardware path: the same
# command works on Intel and on AMD without changing an element name.
gst-launch-1.0 -e -v videotestsrc is-live=true num-buffers=600 ! \
  video/x-raw,framerate=60/1,width=1920,height=1080 ! \
  videoconvert ! mfh264enc ! h264parse ! mp4mux ! filesink location=mf_h264_1080p60.mp4

# Re-encode the real file through Media Foundation.
gst-launch-1.0 -e -v filesrc location=$VIDEO ! matroskademux name=d \
  d.video_0 ! queue ! decodebin ! videoconvert ! \
  mfh264enc ! h264parse ! mp4mux ! filesink location=reenc_mf_h264.mp4


# PROVING THE GPU IS REALLY DOING IT
#
# Three ways, in order of how much they prove. Worth knowing all three,
# because the first one does not work on every card.
#
# 1. THE CAPS, which is structural proof and always available. Look for
#    this line in the -v output of the pipeline above:
#
#      nvh264dec0.GstPad:src: caps = video/x-raw(memory:CUDAMemory)
#
#    memory:CUDAMemory means the decoded frame is in GPU memory and never
#    came back across the bus. No amount of software fallback produces
#    that caps feature.
#
# 2. GPU MEMORY, which is a number. Run the pipeline and sample:
#
#      nvidia-smi --query-gpu=memory.used --format=csv,noheader
#
#    Measured on the GT 730 here: 859 MiB idle, 981 MiB while an
#    NVENC->NVDEC 1080p60 pipeline ran, back to idle afterwards.
#
# 3. UTILISATION COUNTERS, if the card has them. On this GT 730 with
#    driver 475 they do NOT exist:
#
#      nvidia-smi --query-gpu=utilization.gpu,utilization.encoder --format=csv
#        -> [N/A], [N/A]
#
#    and --query-compute-apps returns [N/A] as well. That is the card, not
#    the pipeline: those counters arrived on later consumer GPUs. Do not
#    read the N/A as "the GPU is idle" -- method 2 says otherwise.
#
# A throughput comparison against x264enc is the other obvious check, and
# it is a fair one ONLY on an otherwise idle machine: a software encoder
# measured while the drive is compiling Qt looks far worse than it is.

7. SEND AND RECEIVE OVER RTP
-----------------------------------------------------------------------
# Two shells, sender first. x264enc here, though mfh264enc and nvh264enc are
# both drop-in replacements.
gst-launch-1.0 -v videotestsrc is-live=true ! video/x-raw,framerate=60/1,width=1280,height=720 ! \
  videoconvert ! x264enc tune=zerolatency bitrate=4000 speed-preset=veryfast ! \
  h264parse config-interval=1 ! rtph264pay pt=96 ! \
  udpsink host=127.0.0.1 port=5004

gst-launch-1.0 -v udpsrc port=5004 caps="application/x-rtp, media=video, encoding-name=H264, payload=96" ! \
  rtpjitterbuffer ! rtph264depay ! h264parse ! decodebin ! videoconvert ! autovideosink sync=true

# H.265 out of the real file, decoded with libde265.
gst-launch-1.0 -e -v filesrc location=$VIDEO ! matroskademux name=d \
  d.video_0 ! queue ! decodebin ! videoconvert ! \
  x265enc tune=zerolatency bitrate=4000 ! h265parse config-interval=1 ! rtph265pay pt=96 mtu=1200 ! \
  udpsink host=127.0.0.1 port=5006 sync=false async=false

gst-launch-1.0 -v udpsrc port=5006 caps="application/x-rtp,media=video,encoding-name=H265,payload=96" ! \
  rtpjitterbuffer ! rtph265depay ! h265parse ! queue ! \
  libde265dec ! videoconvert ! fpsdisplaysink video-sink=autovideosink sync=true text-overlay=true


-----------------------------------------------------------------------
8. LOW LATENCY
-----------------------------------------------------------------------
# The receiver pattern: a short jitter buffer, a leaky queue so a late
# frame is dropped rather than queued, GPU decode and GPU render.
gst-launch-1.0 -v \
  udpsrc port=5004 caps="application/x-rtp,media=video,encoding-name=H264,payload=96,clock-rate=90000" ! \
  rtpjitterbuffer latency=10 drop-on-latency=true do-lost=true ! \
  rtph264depay ! h264parse ! \
  queue max-size-buffers=2 leaky=downstream ! \
  d3d11h264dec ! \
  fpsdisplaysink video-sink=d3d11videosink sync=false text-overlay=true

# Screen capture, encoded and sent. Uses NVENC; mfh264enc and x264enc are
# drop-in replacements if the GPU is busy, or not NVIDIA at all.
gst-launch-1.0 -v \
  d3d11screencapturesrc show-cursor=false ! \
  queue ! d3d11download ! videoconvert ! \
  video/x-raw,framerate=60/1 ! \
  nvh264enc bitrate=8000 ! h264parse config-interval=1 ! \
  rtph264pay pt=96 mtu=1200 ! \
  udpsink host=127.0.0.1 port=5004 sync=false async=false

# Lowest latency of all: no re-encode. The file's own H.264 is payloaded
# straight out, so nothing but parsing sits between disk and wire.
gst-launch-1.0 -e -v \
  filesrc location=$VIDEO ! matroskademux name=d \
  d.video_0 ! queue ! h264parse config-interval=1 ! video/x-h264,stream-format=byte-stream,alignment=au ! \
  rtph264pay pt=96 mtu=1200 ! \
  udpsink host=127.0.0.1 port=5004 buffer-size=16777216 sync=true async=false

gst-launch-1.0 -v \
  udpsrc port=5004 buffer-size=16777216 caps="application/x-rtp,media=video,encoding-name=H264,payload=96,clock-rate=90000" ! \
  rtpjitterbuffer latency=5 do-lost=true ! \
  rtph264depay ! h264parse ! \
  queue max-size-buffers=2 leaky=downstream ! \
  d3d11h264dec ! \
  fpsdisplaysink video-sink=d3d11videosink sync=false text-overlay=true

9. WHEN SOMETHING DOES NOT WORK
-----------------------------------------------------------------------
# The environment sets GST_DEBUG=2 and sends it to GST_DEBUG_FILE, so
# warnings are in the log rather than on the terminal. Raise it per run:
GST_DEBUG=3 gst-launch-1.0 videotestsrc num-buffers=10 ! fakesink

# Draw the negotiated pipeline. Files land in GST_DEBUG_DUMP_DOT_DIR.
GST_DEBUG_DUMP_DOT_DIR=$DEVDRIVE_ROOT/logs/gstreamer/dot \
  gst-launch-1.0 videotestsrc num-buffers=10 ! videoconvert ! fakesink

# Caps negotiation failures are almost always readable at level 4 on the
# two elements that failed to agree:
GST_DEBUG=GST_CAPS:4,GST_PADS:4 gst-launch-1.0 videotestsrc ! fakesink
