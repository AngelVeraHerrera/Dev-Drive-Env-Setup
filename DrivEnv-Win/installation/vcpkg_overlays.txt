=======================================================================
WHAT THE OVERLAY PORTS CHANGE, AND WHY
=======================================================================

Why this file exists
-----------------------------------------------------------------------
Every overlay in vcpkg_overlays/ports exists because an upstream port
does not work on this toolchain, and every one of them is a thing that
has to be re-applied when the port is bumped. Knowledge that lives only
in a diff is knowledge that gets lost on the next rebase -- which has
already happened once here, expensively: the directxmath/directx-headers
dependency was solved and written down for a previous environment, the
note did not travel with the overlay, and the same problem was diagnosed
again from scratch months later, presenting as an error about CUDA.

Keep this file next to the ports and update it in the same commit.


gstreamer           (eight deltas, all documented in its portfile head)
-----------------------------------------------------------------------
1. gstfilesink_fix_gcc15-2-Rev11.patch
   gstfilesink.c redefines off_t to guint64 on Win32 but still maps
   ftruncate to _chsize, which takes a long. GCC rejects the narrowing.
   Keep the patch LF-terminated: vcpkg applies patches with `git apply`,
   which refuses a CRLF patch against an LF source.

2. d3d11-winrt-probe-mingw.diff
   gst-plugins-bad's d3d11 enables its UWP sources from a probe that
   does not include <windows.ui.xaml.media.dxinterop.h>, the one header
   mingw-w64 does not ship. WINAPI_PARTITION_APP is true on desktop, so
   the probe passes and the build then fails. The patch adds that header
   to the probe, so d3d11 keeps its desktop features and only the two
   UWP window backends are skipped.

3. d3d11-wgc and d3d12-wgc disabled
   The Windows Graphics Capture backends use WinRT template types that
   mingw-w64's generated headers do not provide the way the MSVC SDK
   does. Upstream exposes these as feature options, so this is a
   supported configuration rather than a patch. Screen capture through
   WGC is what is given up; d3d11screencapturesrc still works.

4. gst_debug=true in release builds
   With gst_debug=false, gstinfo.h poisons gst_debug_log and anything
   that logs fails to compile. Also means GST_DEBUG actually does
   something in the shipped build.

5. directxmath and directx-headers declared under plugins-bad
   The two things the MSVC Windows SDK ships and mingw-w64 does not.
   DirectXMath is what d3d11 needs; DirectX-Headers is what d3d12 needs.
   Nothing in the dependency graph declares either, so without this they
   are present only by accident.

   The portfile header covers this one in full. The failure mode is the
   point:
   both are probed and, when missing, the subdirectory calls
   subdir_done() -- silently. d3d11 disappears, gstcuda disappears with
   it, and the first thing to complain is nvcodec, with a message about
   a missing CUDA dependency. No CUDA toolkit is involved in building
   nvcodec at all.

   KNOWN AND NOT FIXED: gstnvdecoder.cpp guards its d3d11 include on
   G_OS_WIN32 while nothing before that line has included glib, so the
   include only happens because the d3d12 include two lines earlier
   pulls glib in. Enabling d3d12 masks it. Disabling d3d12 later would
   bring it back looking like an unrelated compile error.

6. -Dgst-plugins-bad:d3d11=enabled, where upstream leaves it auto.
   A safety net for exactly the failure delta 5 describes, restored from a
   previous environment's overlay. At "auto" a missing DirectXMath makes
   the subdirectory bail silently; at "enabled" meson stops at the line
   that names DirectXMath. A no-op while delta 5 holds, which is the
   point: it costs nothing now and turns the next silent regression into
   an error where it happens.

7. mediafoundation-winrt-optional-mingw.diff
   The same disease as delta 2, in the plugin next door, and it cost every
   mf* encoder. Fixed: the WinRT half is declined instead of the whole
   subdirectory. mfh264enc, mfaacenc, mfmp3enc, mfvp9enc and the MF
   decoders now exist. mfh265enc does not, and that is the GPU and the OS
   rather than the build.

8. -Dgst-plugins-bad:svtav1=enabled, with svt-av1 declared as a dependency.
   AV1 encoding. Upstream leaves it to auto-detection, and auto-detection
   is what went wrong: the plugin was built against an svt-av1 present
   only as someone else's transitive dependency and dangled when that went
   away. DEPENDS ON THE fastfeat OVERLAY ABOVE -- enabling this without it
   brings back a dangling plugin and, through avcodec, a dead ffmpeg.

fastfeat                                  (one delta, MinGW only)
-----------------------------------------------------------------------
Builds the library WITHOUT the "lib" prefix on anything but MSVC, so the
file on disk is fastfeat.dll.

The port injects its own CMakeLists.txt and its own fastfeat.def, and the
CMakeLists globs *.def into the sources -- so the linker reads the .def as
a module-definition file, and its first line is

    LIBRARY   fastfeat

A LIBRARY statement NAMES the DLL: the linker writes "fastfeat.dll" into
the import library. On MSVC that is true, because MSVC gives a DLL no
prefix. On MinGW, CMake adds "lib", the output is libfastfeat.dll, and the
import library now promises a file nobody installs.

WHAT IT BREAKS, and not one line of it mentions fastfeat:

    svt-av1 links fastfeat            -> builds and installs, no complaint
    libSvtAv1Enc.dll                  -> cannot load, wants fastfeat.dll
    avcodec-63.dll links libSvtAv1Enc -> cannot load
    ffmpeg.exe                        -> dies at startup, 0xC0000135
    libgstlibav.dll links avcodec     -> the whole ffmpeg bridge in
                                         gstreamer disappears: no
                                         avdec_h264, no avenc_aac

Every build in that chain reports success. The first thing to object is a
program trying to LOAD the library, which is why step 5 found it and no
compiler ever would. It had been broken in two environments unnoticed.

The prefix is dropped rather than the LIBRARY line deleted, so the name
upstream chose is honoured and the artefact is called the same thing on
both toolchains.

Worth sending upstream: a real bug on any non-MSVC Windows toolchain, and
MSVC is unaffected either way.


fastdds         (five deltas, MinGW-only, all invisible to MSVC)
-----------------------------------------------------------------------
FIVE LOCAL deltas, listed in the portfile head. The five patches the
portfile also names -- disable-autolink, disable-test, disable-werror,
fix-deps, pdb-file -- are UPSTREAM's and are not deltas; counting patch
files instead of local changes is how "four" became "seven" in an earlier
draft of this file.

The local ones: dllexport on an internal-linkage const, clock_gettime
redefined where mingw-w64 already has it, the gated tool-copy block,
MINGW_COMPILER propagated, and static linkage forced -- which is the one
that matters and is explained below.

BUT THE DELTAS ARE NOT THE INTERESTING PART. This port builds a DLL that
CANNOT BE USED for publish or subscribe on MinGW, and the reason is not in
any patch:

  the DLL does not export     vtable for eprosima::fastdds::dds::TypeSupport
  nor                         traits<TypeDescriptor>::make_shared
  nor                         traits<MemberDescriptor>::make_shared

Nothing that DEFINES a type can therefore link against it -- neither a
type from fastddsgen nor one built through the XTypes dynamic API. Creating
a DomainParticipant works, which is why a smoke test passes and hides it.

Measured 2026-08-27, not inferred. All three symbols are PRESENT in the
compiled objects (nm on TypeSupport.cpp.obj and across the 260 objects of
the release build); only the export table is short. Confirmed from the
other direction too: a real publisher compiles with zero errors and then
fails to link on exactly those three names.

The cause is annotation, in two flavours:
  * TypeSupport marks each METHOD with FASTDDS_EXPORTED_API but not the
    CLASS. GCC exports the methods; the vtable is a separate data symbol
    that only comes out when the class itself carries the attribute.
  * make_shared is declared exported INSIDE a template
    (detail/type_traits.hpp), where GCC ignores the attribute for explicit
    instantiations -- it has to sit on the instantiation directive.

WHAT WAS TRIED AND DID NOT WORK: -DCMAKE_WINDOWS_EXPORT_ALL_SYMBOLS=ON.
CMake generated no .def at all and the symbol count did not move. Fast DDS
manages its own exports and the property never reached the target.

WHAT WORKS: a static Fast DDS. A static archive has no export table, so
the linker takes the symbols straight out of it and the problem is
structurally impossible rather than merely configured away.

There are two ways to get one, and they are NOT equivalent.

  set(VCPKG_LIBRARY_LINKAGE static)   <- in this port's portfile. USED.

vcpkg supports per-port linkage for exactly this, and the mongo family in
this same directory has been doing it for years. The package stays in the
SAME installed tree, so one CMAKE_PREFIX_PATH still finds it, and its
dependencies stay DYNAMIC.

  --triplet x64-mingw-ucrt-static-release   <- also works, NOT used here.

That installs into a separate tree and rebuilds fastcdr, foonathan-memory,
tinyxml2 AND openssl statically. Two consequences: consumers need a second
prefix path, and an application linking Fast DDS alongside Qt or curl ends
up with TWO OpenSSL instances in one process -- one static inside this
library, one from libcrypto-3-x64.dll. Different state, different symbols.
That is the kind of failure this environment keeps being bitten by, so the
lighter mechanism wins.

Both were built and verified. Same 15 checks pass either way: a run-time
XTypes type, a matched writer and reader, and a sample round-tripped with
a double, an unsigned and a string intact. The portfile route produces a
36 MB binary, the static triplet a 44 MB one, and only the latter needs
the fastcdr overlay below.

Reached the heavy tool first and the light one second, which is the wrong
order and worth recording: the question "could the mongo overlays be
replaced by a static triplet?" is what surfaced it. The answer there is
no, and for the same reason.

Worth sending upstream: two one-line annotation fixes would remove the
need for any of this.


fastcdr                            (one delta, static builds only)
-----------------------------------------------------------------------
mingw-static-no-resource.patch -- upstream adds FastCdr.rc to the source
list unconditionally.

A Windows resource script belongs in a DLL or an EXE, never in a static
archive, and windres does not shrug at it:

    windres.exe: no resources
    ninja: build stopped: subcommand failed.

With BUILD_SHARED_LIBS=OFF the guarded body of the .rc compiles to
nothing, windres treats an empty result as an error, and the build dies
before a single object exists. The patch adds the file only for a shared
build, so the dynamic triplet behaves exactly as before.

Needed ONLY by a static-triplet build. fastdds itself no longer requires
it, because forcing linkage in the portfile leaves fastcdr dynamic and
windres is never asked to compile a resource into an archive. Kept because
the static triplet is still available and would hit this immediately.

Delete this overlay if the static triplet is ever dropped.

-----------------------------------------------------------------------
Carries libintl.patch and does not use vcpkg_from_* because the project

vcpkg-qmake                            (one delta, MinGW targets)
-----------------------------------------------------------------------
Selects GNU make instead of jom or nmake when the target is MinGW. The
reasoning is also carried in the header of vcpkg_qmake_build.cmake, and
the port's description field summarises it.

Upstream picks the build tool from CMAKE_HOST_WIN32 alone, so on
Windows it always lands on jom or nmake no matter what toolchain the
TARGET uses. For a MinGW target that is the wrong family: qmake's MinGW
spec emits POSIX recipes (rm -f, test -d, mkdir -p, cp -f) and jom hands
them to cmd.exe, which fails on the first one before anything compiles.
The overlay selects GNU make when VCPKG_TARGET_IS_MINGW.

STILL NEEDED. Upstream at baseline 06d00ff still has the bare
if(CMAKE_HOST_WIN32). Deleting this overlay breaks every qmake-built Qt
port on this triplet.

Worth sending upstream: a real bug for any MinGW target.


graphene                             (one delta: a dependency removed)
-----------------------------------------------------------------------
Port-version 5 with upstream's HOST dependency on "gettext" (default
features off, feature "tools") deleted. That is the whole intent; the
other differences against the baseline are upstream's own port-version
6, which changed the download URLs to download.gnome.org plus a mirror.

Measured 2026-08-26: the upstream commit that FIRST added that gettext
dependency (5618da41e8) is the same one that produced port-version 5,
so this was a deliberate removal, not an old copy that predates it.

PROBABLY OBSOLETE. What it avoids is a host gettext, and gettext is
installed in this environment regardless, pulled in elsewhere in the
graph. If avoiding that build was the only reason for the overlay, it
buys nothing now.

Retiring it means removing the overlay and installing graphene, which
moves the port from version 5 to 6 and rebuilds whatever sits above it.


pango                                         (a stale fork, no reason)
-----------------------------------------------------------------------
No reason is recorded for this one either, and unlike vcpkg-qmake the
diff does not reveal one. The overlay is 1.56.1 port-version 2 while
the baseline offers 1.58.0, with 1.57.0 and 1.57.1 in between. It
fetches a git tag from GitLab instead of the release tarball, omits
upstream's relax-gi-requirement.diff, drops the four meson options that
turn off documentation, man pages, tests and examples, and adds
-Dgtk_doc=false.

That is the shape of a port copied and adjusted before those upstream
changes existed rather than a fix for anything. With no recorded reason,
removing it is not tidying: it is a two-minor-version upgrade of pango
and a rebuild of everything above it. The outcome of doing so belongs in
this file.
