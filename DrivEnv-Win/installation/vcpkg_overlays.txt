=======================================================================
WHAT THE OVERLAY PORTS CHANGE, AND WHY
=======================================================================

Why this file exists
-----------------------------------------------------------------------
Every overlay in vcpkg_overlays/ports exists because an upstream port
does not work on this toolchain, and every one of them is a thing that
has to be re-applied when the port is bumped. Knowledge that lives only
in a diff is knowledge that gets lost on the next rebase -- which has
already happened once here, expensively: the directxmath/directx-headers
dependency was solved and written down for a previous environment, the
note did not travel with the overlay, and the same problem was diagnosed
again from scratch months later, presenting as an error about CUDA.

Keep this file next to the ports and update it in the same commit.


Audit of 2026-08-27: twelve overlays down to three
-----------------------------------------------------------------------
HOW THE QUESTION WAS SETTLED, because the obvious method gives the wrong
answer. Diffing an overlay against TODAY's baseline conflates two
unrelated things: a change made here on purpose, and mere version drift.
An overlay pinning an old version differs from the current port in dozens
of lines that nobody here ever wrote.

So each overlay was diffed against the OFFICIAL port at the SAME version,
recovered from vcpkg's own git history. Whatever survives that comparison
is genuinely local. That one change is what turned "glib carries
libintl.patch for reasons unknown" into "glib deletes one dependency and
nothing else" -- libintl.patch is upstream's, and always was.

Then every surviving delta was checked against the CURRENT sources, and
where a build could settle it, a build was run: baseline ports into a
scratch install root (--x-install-root) so the working tree was never
touched.

RESULT

    glib, graphene, pango           RETIRED -- defect fixed upstream
    libbson, mongo-c-driver,
    mongo-cxx-driver, utf8proc      RETIRED -- static linkage was never
                                    the goal, only a workaround for
                                    older baselines. Dynamic is the
                                    policy here
    fastdds, fastcdr                DEFERRED -- defects all still real,
                                    but DDS is not in use yet and an
                                    overlay nothing installs is pure
                                    maintenance cost. Diagnosis kept
                                    below, ports recoverable from git
    fastfeat, gstreamer,
    vcpkg-qmake                     KEPT, each defect re-verified

EVERYTHING DYNAMIC is the policy, and it now holds without exception.
Fast DDS was the one measured exception -- its MinGW DLL cannot be
linked by anything defining a DDS type -- and deferring it removes even
that. The static triplet stays available as a CAPABILITY, but nothing
uses it.

WHAT THE BUILDS PROVED, as opposed to what reading suggested:

  * Baseline glib 2.88.3 + graphene 1.10.8#6 + pango 1.58.0 install
    clean, exit 0, 28/28 packages, with gettext[core,tools] building
    from source in 14 minutes. The reason those three overlays existed
    is gone.
  * The gstreamer overlay then builds against those NEW versions, exit
    0, from source (vcpkg reported "Restored 0 package(s)", so this was
    not a cached artefact built against the old glib). 111 plugins, 554
    features, d3d11 / d3d12 / nvcodec / mediafoundation all loading.
  * Baseline gstreamer FAILS, twice, at the two points its overlay
    predicts. See deltas 4 and 5 below.
  * Baseline fastfeat reproduces its load failure end to end. See the
    fastfeat section.

COST OF RETIRING glib / graphene / pango: 16 of the 107 installed ports
sit above glib and are rebuilt when its version moves -- the whole Qt
stack, ffmpeg, opencv4, gstreamer, gst-rtsp-server, harfbuzz. On a fresh
drive that costs nothing, because everything is built once anyway. On a
live drive it is hours. This is a change to make at drive generation,
not by forcing a rebuild in place.


gstreamer            (nine deltas, all documented in its portfile head)
-----------------------------------------------------------------------
1. gstfilesink_fix_gcc15-2-Rev11.patch
   gstfilesink.c redefines off_t to guint64 on Win32 but still maps
   ftruncate to _chsize, which takes a long.
   Keep the patch LF-terminated: vcpkg applies patches with `git apply`,
   which refuses a CRLF patch against an LF source.

   NO LONGER NEEDED, measured 2026-08-27, and the only delta of the
   eight that is not. The two #defines are still there (gstfilesink.c:65
   and :67) but the defect cannot fire: the file's ONLY ftruncate call
   is line 687, `ftruncate (fileno (filesink->file), 0)`, and a literal
   0 gives _chsize(int,long) nothing to narrow. The pristine 1.28.6 file
   compiles to a real object with GCC 16.2.0, under -Werror plus the
   project's own full warning list, in three configurations.

   Two things worth knowing before deleting it. The patch's 64-bit
   branch is DEAD CODE: `#if defined(_chsize_s)` is false because
   _chsize_s is a function, not a macro, so the patch still calls
   _chsize(fd, (long) size) and does not buy the 64-bit safety its
   comment advertises. And upstream's `#define ftruncate _chsize` is
   itself wrong on this toolchain for a different reason -- mingw-w64
   does ship a real ftruncate (unistd.h:57, aliased to ftruncate64), so
   the define discards a 64-bit-capable function in favour of a
   deprecated 32-bit one. Latent only, while the sole call truncates
   to 0. Left in place for now: it applies cleanly and costs nothing,
   and removing it means renumbering this list and the portfile head.

2. d3d11-winrt-probe-mingw.diff
   gst-plugins-bad's d3d11 enables its UWP sources from a probe that
   does not include <windows.ui.xaml.media.dxinterop.h>, the one header
   mingw-w64 does not ship. WINAPI_PARTITION_APP is true on desktop, so
   the probe passes and the build then fails. The patch adds that header
   to the probe, so d3d11 keeps its desktop features and only the two
   UWP window backends are skipped.

3. d3d11-wgc and d3d12-wgc disabled
   The Windows Graphics Capture backends use WinRT template types that
   mingw-w64's generated headers do not provide the way the MSVC SDK
   does. Upstream exposes these as feature options, so this is a
   supported configuration rather than a patch. Screen capture through
   WGC is what is given up; d3d11screencapturesrc still works.

   ASYMMETRIC, and re-checked 2026-08-27. Only the d3d12 half still has
   the stated defect: gstd3d12graphicscapture.cpp:69 and :72 do use the
   MSVC-only __FITypedEventHandler_2_..._t typedefs, mingw-w64 defines
   none of them, and compiling those two lines reproduces the quoted
   error verbatim. On the d3d11 side the only WGC source,
   gstd3d11winrtcapture.cpp, never touches those types and compiles
   clean.

   THE d3d11 HALF IS KEPT ANYWAY, deliberately, after proposing to drop
   it and being wrong. "No cost" was the premise and it is false:
   enabling WGC on d3d11 adds five public GObject properties to
   d3d11screencapturesrc, and -- the real objection -- it converts a
   LOUD failure into a SILENT fallback. Today an unsupported DXGI
   capture reaches `unsupported:` and raises GST_ELEMENT_ERROR. With
   the option enabled, that path instead flips to WGC and continues,
   logging an INFO line, into a backend that resolves every entry point
   at runtime through g_module_open against mingw-w64's community WinRT
   vtables. Build-passes / degrades-at-runtime is the exact pattern
   that cost this environment a day on fastfeat.

   If it is ever revisited, the bar is a full meson build AND running
   d3d11screencapturesrc on this toolchain -- not a translation unit
   that compiles.

4. gst_debug=true in release builds
   With gst_debug=false, gstinfo.h poisons gst_debug_log and anything
   that logs fails to compile. Also means GST_DEBUG actually does
   something in the shipped build.

5. directxmath and directx-headers declared under plugins-bad
   The two things the MSVC Windows SDK ships and mingw-w64 does not.
   DirectXMath is what d3d11 needs; DirectX-Headers is what d3d12 needs.
   Nothing in the dependency graph declares either, so without this they
   are present only by accident.

   The portfile header covers this one in full. The failure mode is the
   point:
   both are probed and, when missing, the subdirectory calls
   subdir_done() -- silently. d3d11 disappears, gstcuda disappears with
   it, and the first thing to complain is nvcodec, with a message about
   a missing CUDA dependency. No CUDA toolkit is involved in building
   nvcodec at all.

   KNOWN AND NOT FIXED: gstnvdecoder.cpp guards its d3d11 include on
   G_OS_WIN32 while nothing before that line has included glib, so the
   include only happens because the d3d12 include two lines earlier
   pulls glib in. Enabling d3d12 masks it. Disabling d3d12 later would
   bring it back looking like an unrelated compile error.

6. -Dgst-plugins-bad:d3d11=enabled, where upstream leaves it auto.
   A safety net for exactly the failure delta 5 describes, restored from a
   previous environment's overlay. At "auto" a missing DirectXMath makes
   the subdirectory bail silently; at "enabled" meson stops at the line
   that names DirectXMath. A no-op while delta 5 holds, which is the
   point: it costs nothing now and turns the next silent regression into
   an error where it happens.

7. mediafoundation-winrt-optional-mingw.diff
   The same disease as delta 2, in the plugin next door, and it cost every
   mf* encoder. Fixed: the WinRT half is declined instead of the whole
   subdirectory. mfh264enc, mfaacenc, mfmp3enc, mfvp9enc and the MF
   decoders now exist. mfh265enc does not, and that is the GPU and the OS
   rather than the build.

8. -Dgst-plugins-bad:svtav1=enabled, with svt-av1 declared as a dependency.
   AV1 encoding. Upstream leaves it to auto-detection, and auto-detection
   is what went wrong: the plugin was built against an svt-av1 present
   only as someone else's transitive dependency and dangled when that went
   away. DEPENDS ON THE fastfeat OVERLAY ABOVE -- enabling this without it
   brings back a dangling plugin and, through avcodec, a dead ffmpeg.

TWO METADATA DELTAS THE PORTFILE HEAD DOES NOT COUNT. It used to claim
"exactly EIGHT deltas ... and nothing else", and a full recursive diff
found two beyond the functional ones, both harmless: vcpkg.json gains a
"[MILETHOS] ..." suffix on the description, and it gains a port-version
where the baseline port has no port-version field at all. The head now
says "NINE FUNCTIONAL deltas ... plus two metadata ones", which is a
claim a diff agrees with.

9. gstd3d11config.h relocated out of lib/, and the stale -I dropped
   from gstreamer-d3d11-1.0.pc.

   THE SYMPTOM: the installed gst/d3d11/gstd3d11.h line 28 does
   #include <gst/d3d11/gstd3d11config.h>, and that header was not in
   the installed tree at all. Any C++ consumer of the d3d11 helper API
   therefore failed on a bare "No such file or directory", naming a
   header the port had installed and then removed. Nothing notices at
   build time -- no plugin and no gst-launch pipeline includes it. Only
   code reaching for the d3d11 API directly does, which is exactly what
   a camera path wants to do.

   THE CAUSE IS UPSTREAM'S PORT, not this overlay and not MinGW. Two
   generated headers declare install_dir = libdir/gstreamer-1.0/include:
   gst/gl/gstglconfig.h and gst/d3d11/gstd3d11config.h. The baseline
   port relocates the gl one into include/gstreamer-1.0 and strips the
   matching -I from gstreamer-gl-1.0.pc; it never learned about the
   d3d11 one, whose config header install is newer. Then its own
   file(REMOVE_RECURSE .../lib/gstreamer-1.0/include) deletes the
   directory, taking the d3d11 header with it, and
   gstreamer-d3d11-1.0.pc is left as the ONE .pc still advertising -I
   into a directory that no longer exists. Verified in the baseline
   portfile: zero mentions of gstd3d11config anywhere in it.

   THE FIX mirrors what the port already does for gl -- rename the
   header into include/gstreamer-1.0/gst/d3d11/ before the removal, and
   strip the dangling -I from the .pc, release and debug both. Guarded
   on EXISTS rather than on a feature, because d3d11 comes from
   plugins-bad and is Windows-only, so a feature test would duplicate
   the platform logic that produced the file in the first place.

   Worth sending upstream: it affects MSVC identically, and the fix is
   four lines beside code that already does the same thing one plugin
   over.

   HOW TO TEST IT, because the first attempt produced a false pass. In
   classic mode `vcpkg install gstreamer` reports "already installed"
   from the package NAME and skips the build entirely, ignoring a
   port-version bump. The port has to be REMOVED from the target install
   root first or the new portfile never runs and the old artefacts are
   what gets inspected.

fastfeat                                  (one delta, MinGW only)
-----------------------------------------------------------------------
Builds the library WITHOUT the "lib" prefix on anything but MSVC, so the
file on disk is fastfeat.dll.

The port injects its own CMakeLists.txt and its own fastfeat.def, and the
CMakeLists globs *.def into the sources -- so the linker reads the .def as
a module-definition file, and its first line is

    LIBRARY   fastfeat

A LIBRARY statement NAMES the DLL: the linker writes "fastfeat.dll" into
the import library. On MSVC that is true, because MSVC gives a DLL no
prefix. On MinGW, CMake adds "lib", the output is libfastfeat.dll, and the
import library now promises a file nobody installs.

WHAT IT BREAKS, and not one line of it mentions fastfeat:

    svt-av1 links fastfeat            -> builds and installs, no complaint
    libSvtAv1Enc.dll                  -> cannot load, wants fastfeat.dll
    avcodec-63.dll links libSvtAv1Enc -> cannot load
    ffmpeg.exe                        -> dies at startup, 0xC0000135
    libgstlibav.dll links avcodec     -> the whole ffmpeg bridge in
                                         gstreamer disappears: no
                                         avdec_h264, no avenc_aac

Every build in that chain reports success. The first thing to object is a
program trying to LOAD the library, which is why step 5 found it and no
compiler ever would. It had been broken in two environments unnoticed.

The prefix is dropped rather than the LIBRARY line deleted, so the name
upstream chose is honoured and the artefact is called the same thing on
both toolchains.

Worth sending upstream: a real bug on any non-MSVC Windows toolchain, and
MSVC is unaffected either way.


DEFERRED 2026-08-27: fastdds, fastcdr  (Fast DDS is not in use yet)
-----------------------------------------------------------------------
Both overlays deleted, and NOT because their defects went away. Every
one of them is still present upstream. DDS is simply not being used yet,
and an overlay that nothing installs is a maintenance cost with no
return: it has to be re-reconciled at every baseline bump.

Neither port was ever in vcpkg.packages, so nothing in the normal drive
build installed them; they were installed by hand for the proof of
concept work.

RECOVER THEM WITH GIT, do not rewrite them from this text:

    git log --diff-filter=D -- DrivEnv-Win/vcpkg_overlays/ports/fastdds
    git checkout <that commit>~1 -- DrivEnv-Win/vcpkg_overlays/ports/fastdds
                                    DrivEnv-Win/vcpkg_overlays/ports/fastcdr

What follows is the DIAGNOSIS, kept because it is the expensive part and
because a diff will not tell you any of it.

WHY FAST DDS HAS TO BE STATIC ON MINGW, which is the whole story. The
DLL does not export:

  vtable for eprosima::fastdds::dds::TypeSupport
  traits<TypeDescriptor>::make_shared
  traits<MemberDescriptor>::make_shared

so nothing that DEFINES a type can link it -- neither a type from
fastddsgen nor one built through the XTypes dynamic API. Creating a
DomainParticipant works, which is why a smoke test passes and hides it.
Measured, not inferred: all three symbols are PRESENT in the compiled
objects, and only the export table is short. A real publisher compiles
with zero errors and then fails to link on exactly those three names.

The cause is annotation, in two flavours. TypeSupport marks each METHOD
with FASTDDS_EXPORTED_API but never the CLASS, and GCC only emits the
vtable, a separate data symbol, when the class itself carries the
attribute. And make_shared is declared exported INSIDE a template, in
detail/type_traits.hpp, where GCC ignores the attribute for explicit
instantiations -- it has to sit on the instantiation directive.

WHAT DID NOT WORK: -DCMAKE_WINDOWS_EXPORT_ALL_SYMBOLS=ON. CMake
generated no .def at all and the symbol count did not move. Fast DDS
manages its own exports and the property never reached the target.

WHAT WORKED: set(VCPKG_LIBRARY_LINKAGE static) in the portfile, NOT the
static triplet. Both were built and both pass the same 15 checks -- a
run-time XTypes type, a matched writer and reader, and a sample
round-tripped with a double, an unsigned and a string intact -- but the
portfile route keeps the package in the SAME installed tree, so one
CMAKE_PREFIX_PATH still finds it and its dependencies (fastcdr,
foonathan-memory, tinyxml2, openssl) stay DYNAMIC. The static triplet
rebuilds openssl statically too, so an application linking Fast DDS
alongside Qt or curl ends up with two OpenSSL instances in one process.
36 MB binary against 44 MB, and only the triplet route needed fastcdr.

Reached the heavy tool first and the light one second, which is the
wrong order and worth recording: the question "could the mongo overlays
be replaced by a static triplet?" is what surfaced it.

THE OTHER FOUR FASTDDS DELTAS, all MinGW-only and invisible to MSVC.
Two are load-bearing and two were dormant while linkage stayed static,
because FASTDDS_EXPORTED_API then expands to nothing:

  load-bearing  mingw-no-clock-gettime.patch. TimedConditionVariable.cpp
                defines clock_gettime unguarded inside #if _WIN32 while
                mingw-w64 already declares it in pthread_time.h. Fails
                first, inside the library's own translation unit,
                whatever the linkage.

  load-bearing  the tool-copy block, gated off MinGW. Upstream forces
                COMPILE_TOOLS OFF for mingw, so tools/ is never added
                and fast-discovery-server never exists -- while the
                portfile keyed its copy on VCPKG_TARGET_IS_WINDOWS. The
                library compiles completely and the port then fails
                looking for a binary that was never built.

  dormant       mingw-qos-default-linkage.patch. GCC refuses dllexport
                on a namespace-scope const definition, which has
                internal linkage. Exactly two of the seven QoS defaults
                repeat FASTDDS_EXPORTED_API on the DEFINITION, in
                PublisherQos.cpp and SubscriberQos.cpp; the other five
                do not and compile.

  dormant       MINGW_COMPILER propagated to consumers, without which
                every consumer hits dllimport-on-a-definition.

The dormancy hinges on something narrower than "a static archive has no
export table": src/cpp/CMakeLists.txt emits FASTDDS_DYN_LINK only for a
SHARED_LIBRARY target, and that generator expression is re-evaluated
against the STATIC imported target in the consumer's own configure step.
If upstream ever hardcodes FASTDDS_DYN_LINK, both go live.

FASTCDR, one delta, and it only ever mattered for a static build.
Upstream lists FastCdr.rc unconditionally in its sources, and the file
gates its only real content -- the VS_VERSION_INFO block -- on
fastcdr_EXPORTS, which CMake defines only for SHARED and MODULE targets.
A static build therefore preprocesses the .rc to nothing and windres
treats an empty result as an error:

    windres.exe: no resources
    ninja: build stopped: subcommand failed.

Reproduced verbatim on the untouched 2.3.6 file: exit 1 without
-Dfastcdr_EXPORTS, exit 0 with it. Under the portfile-linkage route
fastcdr stayed dynamic, so the patch was a byte-for-byte no-op there --
it was insurance for the static triplet alone.

WHEN DDS COMES BACK, check these in order before assuming the overlays
are still needed. They were all true on 2026-08-27 against 3.6.2/2.3.6:
  1. does TimedConditionVariable.cpp still define clock_gettime unguarded
  2. does CMakeLists.txt still force COMPILE_TOOLS OFF for mingw
  3. has TypeSupport.hpp gained a CLASS-level FASTDDS_EXPORTED_API --
     that single change retires the static linkage and the dormancy of
     the other two with it
  4. do PublisherQos.cpp and SubscriberQos.cpp still repeat the macro
  5. does fastcdr still list FastCdr.rc unconditionally

Worth sending upstream, and it would remove the need for most of this:
two one-line annotation fixes in Fast DDS, and one guard in Fast CDR.


RETIRED 2026-08-27: libbson, mongo-c-driver, mongo-cxx-driver, utf8proc
-----------------------------------------------------------------------
All four deleted. They forced static linkage and pinned old versions;
the baseline versions are now installed and used -- utf8proc 2.11.3,
libbson 2.3.2, mongo-c-driver 2.3.1, mongo-cxx-driver 4.4.0 -- and both
HelloWorlds build and run against them.

WHY IT IS SAFE, which was the only open question: the static linkage
was never the goal. It was a workaround for older baselines where the
dynamic build failed, and this environment wants everything DYNAMIC.
Once that is settled, nothing in these four overlays was still wanted.

WHAT THEY ACTUALLY CARRIED, by the same-version comparison:

    utf8proc          one line: set(VCPKG_LIBRARY_LINKAGE static)
    libbson           the same one line
    mongo-cxx-driver  that line, -DINLINE_VAR=inline, C++17
    mongo-c-driver    that line, a rewritten fix-dependencies.patch,
                      and scrubbing -lutf8proc out of the .pc files and
                      the exported CMake targets, plus two dead files
                      referenced by nothing (fix-dependencies.patch_
                      and patches/fix-dependencies.patch)

The version pins were incidental. Nobody chose 1.30.6 over 2.3.1; that
is simply where the fork was taken, and mongo-c-driver had drifted a
whole major version behind.

THE ONE THING THAT DID NOT FOLLOW: fastdds is still forced static, and
that is NOT a leftover of the same habit. Its MinGW DLL does not export
the TypeSupport vtable, so a dynamic build cannot be linked by anything
that defines a DDS type. See its own section above. "Everything
dynamic" is the policy; fastdds is the one measured exception to it.

vcpkg-qmake                            (one delta, MinGW targets)
-----------------------------------------------------------------------
Selects GNU make instead of jom or nmake when the target is MinGW. The
reasoning is also carried in the header of vcpkg_qmake_build.cmake, and
the port's description field summarises it.

Upstream picks the build tool from CMAKE_HOST_WIN32 alone, so on
Windows it always lands on jom or nmake no matter what toolchain the
TARGET uses. For a MinGW target that is the wrong family: qmake's MinGW
spec emits POSIX recipes (rm -f, test -d, mkdir -p, cp -f) and jom hands
them to cmd.exe, which fails on the first one before anything compiles.
The overlay selects GNU make when VCPKG_TARGET_IS_MINGW.

STILL NEEDED, but as DORMANT INSURANCE, and the earlier claim that
"deleting this overlay breaks every qmake-built Qt port" was wrong.
Corrected 2026-08-27.

The defect is unambiguously still there: vcpkg_qmake_build.cmake:24-37
has no MinGW branch, nothing in the baseline covers it, and
VCPKG_QMAKE_USE_NMAKE only swaps jom for nmake -- still the wrong
family. Both halves of the failure reproduce today: the INSTALLED Qt
6.11.1 qmake really does emit `DEL_FILE = rm -f` and
`CHK_DIR_EXISTS = test -d`, and handing those to cmd.exe really does
fail on the first one.

BUT IT HAS NO LIVE CONSUMERS ON THIS TRIPLET. qtbase does not use
vcpkg_qmake_build at all -- it is the PRODUCER of qt_release.conf /
qt_debug.conf, not a consumer. Repo-wide the only consumers are
qcustomplot, qscintilla and qwt, none of which is installed. So a green
build of the current package set is NOT evidence that this overlay is
unnecessary; it is evidence that nothing exercised it.

Keep it: nearly free, and it becomes load-bearing the moment any of
those three ports enters the plan, where the failure is immediate and
total -- the first recipe, before one object compiles.

Worth sending upstream as a one-line regression fix: vcpkg's own older
helper scripts/cmake/vcpkg_build_qmake.cmake:26-28 already has the
if(VCPKG_TARGET_IS_MINGW) branch that the new one dropped. If it is
sent, note that this overlay's find_program(... NAMES make
mingw32-make) resolves to the MSYS build of make, which is what
supplies the POSIX shell those recipes need; the legacy branch
hardcodes mingw32-make, which uses cmd.exe unless an sh.exe is on PATH.

The utf8proc deprecation warning is NOT an overlay problem
-----------------------------------------------------------------------
Configuring any mongoc consumer prints:

    CMake Warning at .../share/unofficial-utf8proc/
    unofficial-utf8proc-config.cmake:1 (message):
      find_package(unofficial-utf8proc) is deprecated.
    ... mongocConfig.cmake:67 (find_dependency)

DO NOT WRITE AN OVERLAY FOR IT. This is vcpkg scolding vcpkg. The
caller is injected by vcpkg's own mongo-c-driver port --
fix-dependencies.patch:74 adds find_dependency(unofficial-utf8proc) --
while pristine upstream mongo-c-driver 2.3.1 contains no reference to
that name anywhere; upstream resolves utf8proc through pkg-config. The
message itself comes from the legacy shim that vcpkg's utf8proc port
installs on purpose.

Provably cosmetic, checked end to end 2026-08-27: configure exits 0,
utf8proc::utf8proc resolves to the right import library and DLL,
libmongoc2.dll imports libutf8proc.dll, and the built program prints
"mongoc 2.3.1 utf8proc 2.11.3". message(WARNING) is also unpromotable
to an error, so it cannot start failing a build.

Two reasons an overlay would be actively bad here. It would force a
rebuild of mongo-c-driver and cascade to mongo-cxx-driver, for zero
functional gain. And when vcpkg fixes its own inconsistency, the
overlay becomes exactly the kind of dead weight this audit just spent a
day removing.

If the noise ever costs real signal in a build log, the cheap answer is
consumer-side and needs no overlay and no rebuild: point
unofficial-utf8proc_DIR at a five-line config that does the
find_dependency and the alias without the message. Verified to silence
it completely. Still a hack, still something to remember later.

The shim cannot simply be deleted from the utf8proc port either: poco
depends on it too.
